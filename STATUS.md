# Status

What buildgate does today, what is opt-in, and its known limits. A change
that alters either table updates this file in the same PR. The summary is in
[`README.md`](README.md#status).

## What works

Latest release tag: **`v0.0.14`**. Release tags are `vX.Y.Z`; a tag is cut
only after `make live-smoke` passes on that commit, and other machines
upgrade by tag, not from `main`.

## Ready to merge

What the factory delivers is a pull request that is ready to merge. Each
poll of an open pull request checks it against this bar and records the
result on the ticket (`merge_readiness`), with every item it lacks:

| The bar | Checked against |
|---|---|
| Out of draft, and not stacked on another ticket's unmerged pull request | GitHub |
| Checks pass (a repository with no checks has none failing) | GitHub's status rollup |
| No review thread is open, from any person, trusted or not | GitHub; a thread the factory answered stays open until a person resolves it |
| No reviewer has requested changes | GitHub's review decision |
| Its head is the commit the factory last built: the ticket's build, or the last corrective round or restack replay run accepted and pushed | The run's `ResultSHA` |
| The release decision for that build still allows it | The recorded decision, re-read |
| That build's code review of the whole pull request diff passed | The run's `code_review` gate; a build with code review off does not meet the bar |

| Where it shows | |
|---|---|
| `factoryd status` | `tickets: 1:ready,ready-to-merge` |
| Next step (`status`, the console, `GET /requests`) | "merge <url>: ready to merge", or "<url> is not ready to merge:" and what it lacks |
| Request page | "Ready to merge" on the ticket, or the list of what it lacks |

A reviewer's approval is not part of the bar: where the repository requires
one, GitHub enforces it. Merging stays a person's action.

## Known limits

| Limit | Detail |
|---|---|
| **Copilot is proven on a small scale only** | A `credential_mode: github-copilot` route and the Copilot CLI harness each took one small ticket to accepted through the gateway (2026-10-04), on an individual free plan with `gpt-4.1`. Unproven: a business or enterprise plan's host, a multi-ticket request on this route, and a model served only on `/responses` (the free plan lists such models and answers `model_not_supported` for each; the request does reach Copilot's `/responses` endpoint through the gateway). The route sends the GitHub login token itself as the bearer token; if GitHub stops accepting it, builds fail with the upstream's 401 and the route needs the short-lived token again, which the gateway cannot refresh inside a running sandbox |
| **A review cannot run when the repository's instruction files are in a shape it cannot mask** | Every review reads the instruction files as the base commit holds them (SC-019). The run halts before the review launches (`review_instructions_failed`) when a tracked instruction file no longer matches the result commit, an instruction path is a link to a directory that is not one, an instruction file was converted by the checkout, a path is spelled two ways, or a submodule sits under an instruction path. The cause is in the review attempt's `review_instructions_error`. The table of instruction paths is a list: a harness that loads a path not on it is not covered |
| **A script under `.factory/` is only as trusted as the files it calls** | Every build, verify and gate sandbox mounts `.factory/` read-only as the commit `.factory.yml` was read from holds it, so a build cannot edit a script a gate runs from there. A script that calls files outside `.factory/` (`scripts/check.py`, a `Makefile` target, as `verify_command: make test` does) runs the build's copy of them. A command that writes into `.factory/` fails. The run halts (`factory_dir_failed`) when the run's worktree lacks the directory the commit has, when `.factory` is a file or a symlink there, or when another spelling of the name exists; no mountpoint is created for it |
| **Repository memory holds only what someone wrote down, unchecked** | A candidate line comes from a build that ended without passing, or passed after a round that did not, and whose notes turn ran, or from `factoryd memory add`; a ticket whose build passed in its first round leaves none. The notes turn after a pass is proven by tests only: no live run of it on any harness yet. No command a line names is run or verified: the person who approves the spec and merges the pull request is the check. The text rule is pattern-based: it refuses absolute paths and any unbroken token of 20 or more characters that mixes letters and digits, so some true notes are refused, and a short internal name passes it. A full section refuses a proposal until `-remove` names a line; nothing is collected, proposed, dropped or retired automatically. |
| **A saved prompt is what the build's session folder held** | The prompts under a run's `prompts/` are copied by the host from the launch's session folder in the worktree, which the coding agent can write: a build can alter, add or hide its own saved prompts before the copy, and the build script has no channel to the host the agent cannot also write: its output file is in a directory the whole sandbox writes, the sandbox denies every set-id system call (no second user for the agent), and a child of the same user reaches its parent's descriptors through `/proc`. For the same reason a round or agent line of the progress feed (`source: worker`) is what some process in the sandbox wrote, the script or the agent: it is display only, never read by a gate, and cannot be recorded as a factory line. The host empties the folder before every launch, so a file from an earlier step is never kept as a later launch's prompt; `factoryd logs -list` and the run page label them "as saved by the build". |
| **Your own worker image needs a `make` built without `posix_spawn`** | OpenShell's sandbox denies every set-id system call, and a stock GNU make resets ids for each recipe line, so every recipe fails with "Operation not permitted". The image `make install` builds carries such a make; an image built on it (`make project-sandbox-image`) inherits it. Tools that switch user (`su`, `sudo`) fail the same way |
| **Docker Desktop cannot run a sandbox** | Its VM's kernel has no Landlock and its daemon no AppArmor, which every sandbox requires, so every launch fails while the gateway and the meter answer; `doctor` fails its "Docker can run sandboxes" row. On a Mac, Docker runs in colima with `sshfs` or `virtiofs` mounts, not `9p` (USAGE.md, "Data directory and colima") |
| **On colima, every container is a local caller** | colima forwards `host.docker.internal` to the host's loopback and adds no forwarding header, so a container reaches `serve` as the console on this machine does: with no tokens configured it reads every request and run and approves a gate. `factoryd install-service -require-tokens` makes every read and write need a token; the console on this machine gets a console token, which does not expire and works only from this machine, in the link `factoryd console` opens |
| **OpenShell 0.1.2 is young** | CPU and memory limits apply, but swap is twice the memory limit and the process limit is one value for every sandbox (1024). A worker can send a model request with a token it invents (the supervisor forwards a header the worker writes itself). The meter listens in plaintext on the Docker VM's loopback. A repository must be under your home directory. Each step that reaches the network starts 10 to 12 s after its sandbox, once the supervisor has rebuilt its proxy (a model route, the registry proxy, a compose service). [`containment-matrix.md`](containment-matrix.md) lists each residual |
| **A lost step is never retried automatically** | A laptop sleep, a lost worker, a stopped, crashed or rebooted `factoryd` (`stop -force`, `upgrade`), a Temporal server that stops answering (a stall of up to about 90 s loses nothing; a longer one parks the request once as `temporal_unreachable`, or `worker_lost` when the server timed the step out first), a sandbox that cannot be started, a model route that does not serve a build or an unreachable package registry halts the run, and a review that gives no verdict leaves it quarantined and kept; a lost build keeps its worktree (not one that was running on an existing branch, such as a corrective round or a retry continuing an attempt: that one can only be rebuilt with `resume -from scratch`). The request waits in `resume_review` and reminds you until you choose: `factoryd resume <id>` continues the build from the last completed round (fresh agent session plus a short handoff; refused when a container of the lost run is alive or the worktree's history changed) or reruns a lost drafting or planning step; `resume -from scratch <id>` rebuilds the ticket; `cancel <id>` withdraws it. A `worker` rebuilds the ticket from scratch at its next start. On macOS an idle Mac does not sleep mid-build (`caffeinate`); closing the lid still does |
| **Builds that need the repository alone can wait a long time** | Requests on one repository build concurrently, each in its own worktree and branch. A `-repository` run, a corrective `-on-branch` round, a retry that continues on the failed attempt's branch, the daemon's reclaim and `factoryd reconcile` need every other build off the repository: they retry every 30 s without holding a job slot, and the lock has no writer preference, so while isolated builds keep overlapping they can wait indefinitely. Stranded worktrees are cleaned only when the repository is idle; `reconcile` reports it busy until then |
| **A restack has limits of its own** | The replay run's own worktree is checked out as any run's is, attributes and filters included (only the host's replay and its git reads are attribute-hardened). A ticket whose runs were recorded before `stack_base_sha` existed is never restacked: its pull request is held, and the operator retargets it by hand. Each restack runs every gate and review again, at the model cost of those reviews (no round budget is used). Only SHA-1 repositories can be restacked (the replay reads attributes from SHA-1's empty tree). The host's git must be 2.41 or later (`git --attr-source`); an older one parks the request, and `doctor` warns |
| Cold Go caches | Every worker container starts with an empty Go build/module cache (a worker-writable cache must never feed canonical verify), so each phase of a Go run compiles cold; on a large repo this is the main wall-clock cost |
| Narrow live coverage | Live validation covers a small fixture set (`testdata/fixtures`, todo-service, todo-kafka-service, the proving-ground corpus, the operator's own repos). Multi-module `go.work`, cgo and generated code are unproven. Private Go modules are proven on one fixture (`make live-private-module`), with a file `GOPROXY` standing in for a company's |
| Languages without a built-in toolchain | Generic runs require an operator-selected image with the language tools and dependencies already available. The compiled, advisory profile contract describes working-tree root markers, binaries, version sources, image/cache support, command candidates, test patterns, and baseline result parsing; profile-only binary hints are warnings, while committed `.factory.yml` requirements are checked against the configured base image and final worker image. Profiles do not install runtimes or dependencies, select images, or affect acceptance; root detection does not resolve nested or monorepo layouts. Automatic toolchain derivation covers Go, Python, Java with Maven (not Gradle), and Ruby with Bundler; Node uses the configured worker image. `make project-sandbox-image` can pre-bake Go modules, npm, Maven, Ruby Bundler, and pip dependencies. The per-run registry proxy routes Go modules, npm, PyPI, Maven Central and RubyGems traffic regardless of a specific manifest file. Baseline named-failure parsing remains limited to Go and pytest |
| The PR budget is a guess | The estimate in `Estimated-Changed-Lines:` is the planner's own, before any code exists. Nothing compares the finished diff with `pr_budget_lines` (the console only shows both); `release_max_insertions` and `release_max_files_changed` are the hard limits |
| Requests in flight at an upgrade keep the earlier build input | A request submitted before `factoryd upgrade` finishes with ticket builds that do not carry the approved spec, no read-back answers in the build input and no PR budget at `plan_review` (USAGE_REFERENCE.md, "Upgrading with requests in flight"). Cancel and submit again to get the new shape |
| Oracles | Opt-in; default-on is undecided (`make bar`) |
| Code review off by default on the CLI | Until you opt in (or use `quickstart`, which writes `required`), correctness rests on `spec_conformity`, the deterministic gates and the human gates |
| CI | Manual-only; run `make ci` before merging a pipeline change |
