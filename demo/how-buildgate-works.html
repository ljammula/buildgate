How Buildgate works

Buildgate (factoryd) turns a ticket into a pull request that a coding agent built and the factory proved. You approve the spec and the plan; the agent builds in a sandbox; the factory's own checks decide whether it passed; you merge.

Why

Coding agents write plausible code fast, but three things stop us handing them tickets unattended:

  • Their "done, tests pass" is a claim, not evidence. An agent can skip a test, weaken one, or stray outside the ticket.
  • They run on our machines with our credentials. An agent with network access and a token is a supply-chain risk.
  • An unexplained diff is slow to review. A reviewer needs to know what was asked, what was checked and what wasn't.

Buildgate's answer is four rules, enforced in code rather than asked of the agent in a prompt:

Contain the agentA sandbox with no network interface; the model is reached only through a supervisor that holds the credential and a meter that enforces budgets
Trust evidence, not claimsEvery stage advances on checks the factory runs itself, recorded with exit codes and hashes
Humans decidePeople approve the spec and plan before code is written, and merge the result
Never mergesThe factory opens a PR at most. Merge and deploy are permanently human, by design

What

A Go daemon (factoryd) with a web console, running on your machine.

InA ticket (text or a GitHub issue) and a git repo with a verify command (go test ./..., make verify…)
OutA PR with an evidence trail, or a quarantine that names the gate that failed
Human gatesSpec review, plan review, (opt-in) acceptance-test review, PR review and merge
Runs onA background worker on Temporal (started for you when it is down), so an interrupted build waits for your decision with its work kept. See What runs on your machine

Three roles, any supported agent

Each request runs three model roles. The session config binds each to a model route, a model and a coding-agent harness: pi (default), codex, copilot or pifork. Changing either changes nothing about the sandbox or the gates.

RoleRunsRequester can choose it?
planningSpec and plan draftingWithin the role's allow-list
executionThe build and its corrective roundsWithin the role's allow-list
reviewAcceptance-test drafting, spec_conformity, code_reviewNever: the requester can't pick a lenient reviewer
 
roles:
  planning:  { model: luna, harness: pi }
  execution: { model: luna, harness: codex, skills: [buildgate-tdd, go-service] }
  review:    { model: luna, allow_shared_model: true }   # same backend as execution needs this opt-in

Skills: every harness loads the repo's own .agents/skills for the build (codex and copilot in every job). Eight worker skills ship inside factoryd, opt-in per role: buildgate-tdd and buildgate-diagnosing, plus go-service, typescript-service, flutter-app, kafka-processing, postgres-change and temporal-go. They reach the worker as a hashed, read-only snapshot; no host ~/.codex or ~/.claude is ever mounted.

    • worker refuses to stop mid-build unless forced. A forced stop, crash, reboot or laptop sleep halts the run and nothing reruns the lost step on its own: the request waits in resume_review with the build's worktree kept, until you run factoryd resume <id>, resume -from scratch or cancel. A shared local model host and compose sidecars are locked host-wide, so jobs queue rather than collide.
    • Temporal: every build runs on it, and factoryd starts it with Docker when it is down (with FACTORYD_AUTOSTART=0 an address must be given). A resumed build continues in its kept worktree with a fresh agent session and a short handoff. It adds workflow history in its Web UI (localhost:8233), and -repository serializes all runs on one repo.
    • OpenShell gateway and meter: two containers in the Docker VM, started with the worker (or by factoryd doctor -fix). The gateway is the only thing that creates a worker container; each sandbox gets its own supervisor, the worker's one route out. Both listen on the VM's loopback only, and the gateway accepts only factoryd's client certificate.

    Inside the build

    Everything the agent can touch is inside the sandbox. Everything that decides whether it passed runs outside it.

    The gates

    A build is accepted only when every gate passes. The factory runs each one after the agent stops and records result, exit code and log hash; the PR body lists each as pass, FAIL or not configured. A failure with rounds left goes back to the agent with the failure attached; otherwise the run is quarantined at that gate.

    Examples use the running ticket: add Multiply(a, b int) int to mathops. The approved plan allows mathops.go and mathops_test.go, requires mathops.go to change, and verifies with go test ./mathops/...; the repo's full suite is go test ./....

    GateWhat it checks, and why the agent can't game itExample it catches
    canonical_verifyThe ticket's verify command passes. The factory reruns it itself; the agent's own run is only a self-checkThe agent reports "tests pass", but Multiply returns a + b; the factory's go test ./mathops/... fails Multiply(3, 4) = 7, want 12
    diff_scopeEvery changed file is in the plan's allowed files, checked on the final commitThe agent also bumps a dependency in go.mod. Not an allowed file, so the run is quarantined (the proving-ground's scope-violation fixture)
    required_files_changedEvery file the plan says must change didThe agent decides an existing helper already multiplies and only adds a test; mathops.go is unchanged, so the gate fails
    tests_addedAt least one test file changed, unless the ticket opted out with a stated reason (recorded on the release decision)Multiply is correct and verify passes, but no _test.go changed
    full_suite_verifyThe repo-wide suite still passes, not just the ticket's testsWhile there, the agent changes the signature of mathops.Divide and updates its tests; ./mathops passes, but package report, which calls Divide, no longer compiles under go test ./...
    spec_conformityEach acceptance criterion is met by the diff, judged by the review role, never the builder. An opinion, so it sits beside the deterministic gatesCriterion 2 says "including zero and negative inputs"; the agent's table test only has positive cases. Verdict: criterion 2 not evidenced
    code_reviewCorrectness review with structured findings posted to the PR, in the same review-role call. Under required (what quickstart writes) a high finding quarantines; advisory never blocksThe test computes its expected value by calling Multiply itself, so it can never fail: flagged as a test that proves nothing
    reference_oracle + canaryThe human-approved acceptance tests pass. They were drafted from the spec before any code existed, are hash-pinned and mounted read-only. The canary reruns the gate with a copy that must fail; if that copy "passes", the tests aren't really running and the gate fails closedThe approved oracle expects Multiply(-2, 5) == -10; an implementation that returns abs(a*b) fails it. Or the agent adds a TestMain that exits before any test runs: the canary passes too, so the gate fails

    .factory.yml can add lint, security_audit, unit_tests and integration_tests gates, each with its own exit code and log.

    Outcomes

    Accepted

    All gates passed. The branch carries BUILD_REPORT.md and BUILD_EVIDENCE.json; a draft PR opens and is marked ready once checks pass.

    Quarantined

    A gate failed, or the corrective rounds ran out. The triage note names the gate and likely cause. Nothing reaches a PR.

    Halted

    A crash, timeout or environment fault. factoryd retry <id> once fixed. A worker lost mid-build (sleep, crash, stop) leaves the request in resume_review with its work kept: factoryd resume <id>.

    factoryd inbox lists everything waiting on you, with the command to act on each.

    What the agent can't do

    • Reach the internet: it has no network interface. Its only route out is its sandbox's supervisor, which admits one model upstream; packages come through a registry proxy
    • See model credentials: it holds a placeholder, and the supervisor substitutes the real one on the way out
    • Spend past the budget: every model call passes the meter, which refuses one past the token or cost ceiling
    • Edit the approved spec or acceptance tests: hash-pinned, tests mounted read-only
    • Choose its reviewer or declare itself done: only factory-run gates accept
    • Merge or deploy: a human does that, outside Buildgate

    Threat model and invariants SC-001 to SC-017: safety-contract.md and containment-matrix.md, both enforced by tests.

    Extend it

    Most extensions are configuration. The ones that need code have a fixed, small footprint, so a new agent or gate can't quietly widen the trust boundary.

    Evidence

    • Tested like it tests agents: Go tests under the race detector, a Python suite covering every harness adapter, and console tests. CLAIMS.md maps every safety claim to the test that enforces it; a claim citing a missing test fails the build.
    • Live runs gate pipeline changes: make live-smoke runs real tickets through the real gateway, sandbox and meter before merge. The worst bugs found so far were invisible to unit tests and review.
    • Proven live on: a fixed corpus of accept and must-quarantine tickets, with no false accepts; real GitHub issues; a service with Postgres, Kafka and Redis; real bugs in three repos, merged by a human; and resuming a build with factoryd resume after a laptop sleep and after a kill -9 of the worker mid-build (the earlier work kept).

    Cost: Codex alone vs Buildgate

    One feature (a REST report plus a read-only MCP tool) built four ways on gpt-5.6-luna from the same commit, scored by 12 hidden acceptance tests written beforehand. Costs at OpenAI's standard rates.

    ArmHidden testsRepo suiteCostWall-clock
    Codex CLI, medium effort12/12fails$0.054 min
    Codex CLI, max effort12/12passes$0.2423 min
    Buildgate, two review calls per ticket12/12passes$0.3358 min
    Buildgate, one combined review call (current)12/12passes$0.2444 min
    • Same money, more output. At $0.24, Buildgate matched a max-effort Codex session but also produced an approved spec, a plan, three sandboxed tickets with seven gates each, and reviewable stacked PRs.
    • Cheapest isn't cheapest. Medium-effort Codex was 5× cheaper but left the repo's own test suite red. Buildgate's canonical_verify refuses exactly that.
    • The cost is time. Buildgate took about twice as long as max-effort Codex (44 vs 23 min): spec and plan drafting, per-ticket sandboxes and gates.
    • Read as signal, not statistics: one request, one run per arm. Run-to-run planner variance is as large as some differences.

    On a ChatGPT or Copilot subscription these are API-price estimates; the subscription is what's billed.

    Not yet proven

    • Our repos: fixtures are personal repos. Multi-module go.work, cgo, private modules and generated code are untested.
    • Routes: live runs mostly use the ChatGPT Codex route; the Copilot route and CLI harness have each taken one small ticket to accepted, on an individual free plan.
    • Acceptance-test drafting: opt-in; drafted tests still need a careful human read.
    • A lost build step is never retried automatically: the request waits in resume_review for your decision, and the build keeps its worktree.

    Try it

    make install installs the tools the Mac lacks, starts Docker and asks which model to use. Keep the repo under your home directory, and use a throwaway one first.

    git clone https://github.com/ljammula/buildgate.git && cd buildgate
make install                       # tools, factoryd, every image; asks for the model
factoryd doctor                    # Docker, images, model route, Temporal, gateway, meter

# Config, Temporal, gateway and meter, worker, console, submit; stops at the first human gate
factoryd quickstart ~/code/your-repo "Add X to Y"

factoryd inbox                     # what's waiting on you
factoryd approve <request-id>      # or approve in the console
factoryd watch <request-id>        # follow the build
factoryd stop                      # stop what quickstart started
