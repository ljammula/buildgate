# Containment escape matrix

Status: reviewed against the current implementation (2026-10-04). This
table is the **current-status snapshot only**. The round-by-round history
(what was found, how, and how it was fixed) is kept outside this repo;
don't duplicate it here.

## Scope: single engineer, one Mac, unattended queue (decided 2026-09-10)

The operating model this matrix defends: **one engineer running
`factoryd worker` unattended on their own Mac against their own
repositories**. The containment goal is exactly one thing: an agent inside
a run cannot escape the container or modify the machine. Met by controls
that are all default-on and real-engine-validated: Docker sandboxing with
no host-execution path on any entry point (`factoryd <run>`, `serve`, the
API, Temporal, `worker`), every worker launched by the OpenShell gateway
with no network interface and the per-sandbox supervisor as the only route
out, a filesystem policy (Landlock, required) that opens only the paths
the launch names, no Docker socket, and a single writable bind mount
scoped to the per-run worktree. One layer down, the Docker backend's VM
(colima on macOS) is set up to share only `~/buildgate` read-write and the target
repositories read-only (USAGE.md, "Data directory and colima"), so an
escape from the container into the VM still does not reach the rest of
`$HOME`; `factoryd doctor` warns on macOS while the VM shares all of it.

Two residuals in the Filesystem row (group-write spanning any process
sharing factoryd's GID; host-visible UID attribution on colima's
shared-folder mount) are **accepted, not scheduled** — both are
attribution/multi-tenant concerns, neither gives a worker a path outside
its own worktree. Multi-tenant isolation is out of scope (the
`tenant`/`tenantspend` packages were removed 2026-09-10 as dead weight
under this same decision). Reopen either only if the operating model
changes (a shared daemon, or more than one person's credentials on one
host).

## Sandbox topology

```text
  HOST (factoryd)               SANDBOX VM (colima)
  +--------------+   mTLS      +--------------------+
  | factoryd     |------------>| OpenShell gateway  |
  | -data-dir    |  sandbox    | VM loopback :17670 |
  | (durable     |  request,   | Docker socket,     |
  |  run records)|  credential | credential store   |
  +--------------+  push       +---------+----------+
        ^                                | creates, digest-pinned image
        |                                v
        | worker output         +-----------------------+
        | file, meter           | worker container      |
        | ledger (host          | NetworkMode none      |
        | paths)                | filesystem policy     |
        |                       | worktree rw at        |
        +--- isolated worktree, | /workspace            |
             rw, bind-mounted   +-----------+-----------+
             per run                        | only route out
                                            v
                                +-----------------------+
                                | supervisor (one per   |
                                | sandbox): admits a    |      +-------------+
                                | destination + binary  |----->| meter       |
                                | + path, substitutes   | each | VM loopback |
                                | the credential        | call | :17672      |
                                +-----------+-----------+      | ceilings,   |
                                            |                  | ledger      |
                                            v                  +-------------+
                                   +-----------------+
                                   | upstream model  |
                                   | (ChatGPT, an    |
                                   |  API, local LLM)|
                                   +-----------------+
```

The worker can reach its supervisor and nothing else; the supervisor
admits only what the run's policy names; only factoryd can reach
`-data-dir`. Live-validated against the real gateway (`OPENSHELL_LIVE=1 go
test ./internal/openshell -run Live`, `make live-smoke`, `make
live-compose`), not just unit tests.

## Matrix

| Boundary | Probe | Current control | Status | Required response |
|---|---|---|---|---|
| Filesystem | Worker writes outside selected workspace | Every worker is launched by the OpenShell gateway from a digest-pinned image built from source (no host-execution path); the image's `WORKDIR` is `/sandbox` and the isolated per-run worktree is bind-mounted read-write at `/workspace`; its external Git common dir and a linked worktree's `.git` pointer file are read-only binds. The filesystem policy (Landlock, `compatibility: hard_requirement`, so a kernel without it fails the launch) denies every path it does not name: read-write `/workspace`, `/tmp`, `/home/worker`, the per-launch output mount, `/dev/null` and, when mounted, the per-launch `/scratch` cache; read-only `/usr`, `/etc`, `/opt`, `/proc`, `/dev`, the guard mount, `/inputs` and the Git common dir (`LaunchSpec.sandboxMounts`). `/tmp` (noexec) and `/home/worker` are size-capped tmpfs mounts; memory and CPU limits are applied through a per-launch workload template; the wrapper sets `ulimit -c 0` and `ulimit -n 4096`. Worker runs as the image's dedicated non-root UID (`sandbox.DefaultWorkerUID`, 65532); group-write on the worktree is granted per run and reclaimed by the worker wrapper on exit. **Residuals of the gateway launcher, accepted:** no Docker read-only root (the root is unwritable to the worker by UID and by the filesystem policy), AppArmor is Docker's `RuntimeDefault` profile, swap is twice the memory limit, the PID limit is one value for every sandbox (`sandbox_pids_limit` in the gateway configuration, 1024), no nproc ulimit. OpenShell's seccomp filter denies every set-id syscall, so a worker image needs a `make` built without `posix_spawn` (the worker image builds one); a stock GNU make cannot run a recipe. `-reference-oracle-dir` (when configured) is bind-mounted read-only into `/workspace`, on both the post-build gate and, opt-in, the build phase's own retry loop; every mount is snapshotted and SHA-256'd before mounting (`sandbox.SnapshotReferenceOracle`), closing a TOCTOU window. `release.MergePolicy.AllowUnsandboxed` (default false) is a release-decision backstop, not a launch option. colima is set up (USAGE.md) to share only `sessionconfig.DataRoot` (`~/buildgate`, where the default data dir and every live script's scratch dir live) read-write and the repositories read-only, never all of `$HOME`; `doctorCheckHomeNotShared` warns (advisory, macOS) when a container can still see `$HOME` itself. **Operator-held residual:** the VM's kernel is the boundary between a worker and those shared folders, and colima's VM installs no updates on its own -- keep it patched (`colima ssh -- sudo apt-get full-upgrade`, then `colima restart`). **Open residuals** (need daemon-level `userns-remap`, not implemented): group-write grant widens to any process sharing factoryd's GID; UID attribution depends on the Docker backend's bind-mount behavior (works on native Linux, not colima's shared-folder mount) | partial | Terminate and quarantine |
| Network | Worker contacts an arbitrary destination | The worker container's `NetworkMode` is `none` on every step; its only egress is its sandbox's supervisor. A step with no model route gets a policy that admits nothing. A model-backed step gets one provider and one policy for exactly one operator-configured route (one upstream host, one credential) — route fallback (`modelrole.SelectRoute`) happens only before launch, host-side, never mid-run: the policy names the upstream, the admitted path (exact for a `chatgpt-codex` or `github-copilot` route, a prefix for a static route; a path rule exists only where the endpoint is a `rest` rule), and the harnesses' model executables. The credential never enters Temporal's persisted Workflow input. A route the runtime cannot serve is refused at launch: a credential to a plaintext upstream, and a route with no worker model id (`RoutePolicy.RouteAccess`). On a `github-copilot` route the meter also overwrites the client headers the Copilot API requires (`CopilotExtraHeaders`), whatever the worker sent. Every model request passes through the meter (`on_error: fail_closed`), which enforces the run's absolute token/cost ceilings and writes each sandbox's ledger on a host path no worker mounts; factoryd reads the ledger after the step and halts the run (`HaltReasonRelayCeilingExceeded`) on a refusal at a ceiling or an unreadable ledger. A request the client dropped before its response completed is charged its estimate and marks the spend partial. Real-engine-validated (`make live-smoke`, the ceiling and path-rule checks of the `internal/openshell` live tests). **Open residual:** a worker can send a token it invents in a header it writes itself; the supervisor forwards it | partial | Block and quarantine; distinct halt reason on ceiling exhaustion or unconfirmed usage |
| Crash recovery | factoryd crashes between launching a worker (or a sidecar) and its own deferred cleanup; or the gateway restarts and starts a worker's command again | Each run appends the name of every sandbox it creates to `<run dir>/sandboxes.jsonl` before the launch. `ReconcileOrphans`, `RemoveRunContainers` and `WorkerContainerPresentForRun` find a recorded sandbox's worker and supervisor containers by the `openshell.ai/sandbox-name` label and remove them once the run reaches a terminal state or its owner heartbeat goes stale; a request resume also asks the gateway (`ResumeGate.Sandboxes`), and a sandbox still held, or an unreachable gateway, refuses the resume. The registry proxy's and compose services' containers and networks carry the `-data-dir` label and are reaped the same way. A gateway restart re-runs every sandbox's command: the worker wrapper runs the command only when a per-launch guard file says it has not started before, a second start exits 97 without touching the worktree, and the step is recorded lost (`ErrSandboxRerun`; a build keeps its worktree, SC-017). Restart guard live-validated 2026-10-04 | enforced, real-engine-validated | Reap on next reconciliation pass; record a rerun step lost |
| Credentials | Worker inherits factory bearer tokens | No host-execution path exists — build/verify/full-suite subprocesses only ever run inside the Docker-sandboxed worker, which sees only the fixed environment allowlist `LaunchSpec.SandboxRequest` builds, never this process's own environment. The request driver's spec/plan/oracle-drafting jobs (`cmd/factoryd/spec_draft_job.go`/`plan_tickets_job.go`/`oracle_draft_job.go`) run every real invocation through the same Docker sandbox a ticket build uses (`runSandboxWithRetries`), each keeping an unsandboxed fallback branch reachable only under `workerConfig.allowUnsandboxedSpecDraft` (no operator-facing flag, exercised only by this repo's own tests). `internal/runner`'s own allowlist (fixed baseline: `PATH`/`HOME`/`LANG`/POSIX locale vars/`TZ`/`TMPDIR`/`USER`/`SHELL`) governs only that test-only branch's subprocess environment, a narrower, separate mechanism. Every drafting job's own sandboxed container is given a deadline sized to outlive its script's own configured wall-clock budget by a fixed margin plus slack (`requestJobContainerDeadline`, `sandboxAttemptMargin`), so the script's own timeout normally fires before Docker kills the container; time spent waiting on the single-instance model-host lock (or starting a sidecar) still comes off that deadline, so under lock contention the sandbox's deletion can come first. `LaunchSpec.Validate` separately rejects `GIT_CONFIG_GLOBAL`/`SYSTEM` for a sandboxed worker's `Environment`. A request's `Harnesses`/`Models` selection (SC-015) resolves only against `internal/harness`'s compiled-in registry and the operator-configured `models:`/`routes:` tables (`routes:`/`models:`/`roles:` is the only session-config schema for them (`roles.<role>.skills` adds only skill names, resolved through the operator's `skill_dirs:`; see the Skills row)) — none of these can name an executable, interpreter, upstream URL, path prefix, route, or credential source. A route's credential (a static key, a `credential_mode: chatgpt-codex` route's access token and account id, or a `credential_mode: github-copilot` route's GitHub login token, which the Copilot API accepts as a bearer token and which does not expire during a step) is resolved host-side, fresh per launch, never into Temporal's persisted input: `cmd/factoryd/route_credentials.go`'s single `resolveRouteCredentials` resolves it only in the process launching that route's worker, and only for the one route `modelrole.SelectRoute` chose for that job — the build, conformity/review, and drafting paths all share this one resolver. factoryd pushes it to the gateway as a provider immediately before the launch and refuses a credential that expires within the step's budget; the worker's environment holds an `openshell:` placeholder, and the supervisor substitutes the value only on a request to the endpoint the route's profile binds. The store is the gateway's database on the VM disk (`/var/lib/openshell/gateway.db` with its `-wal` and `-shm` files, owned by root), encrypted with a key beside it (`/var/lib/openshell/.local/state/openshell/gateway/credentials/key-encryption-key.bin`): disk access on the VM is plaintext access. The gateway's TLS and JWT keys are on the VM disk too (`/var/lib/openshell/tls/`), not in the shared data dir; the factory's client key is `~/.config/factoryd/openshell/mtls/tls.key` (0600). Removing the stack's state means removing the whole `/var/lib/openshell` tree. **Residuals:** a credential header the worker writes itself is forwarded; the supervisor resolves a placeholder the worker puts in the URL path or query of a request to the bound endpoint as well as in a header (never in a body: `request_body_credential_rewrite` is not set), so an upstream that echoes its request URL in a response would return the value to the worker -- a static route's prefix-admitted path leaves room for that, an exact path only the query; the supervisor's handling of an upstream redirect is untested; a credential pushed during a step reaches only sandboxes started after it, so no route may depend on a token refreshed mid-step (a `github-copilot` route therefore carries the login token, not the short-lived exchanged one, which only the host-side model listing uses). `sandbox.PreflightGitCredentials` parses the worker's mounted (read-only but readable) `.git/config` and any `config.worktree` host-side before any mount is built, and refuses launch — fail-closed — if the target repo's own git config embeds a credential (`credential.helper`, `http.extraheader`, a userinfo remote URL); the same check backs `factoryd doctor`. **Model listing extends this boundary to host-side calls that never touch the sandbox**: `doctor -list-models`, `doctorCheckCopilotModelListed`, and the Copilot token-exchange client validate via `sandbox.RoutePolicy.ValidateUpstreamScheme` + `sandbox.CredentialSafeForUpstream` (the same check `RouteSpec.Validate` applies) and refuse redirects (`meter.NoRedirectCheckRedirect`) before ever sending a credential — fixed 2026-09-25 (PR #259) after a review found the Copilot listing path skipped the plaintext-credential rule | enforced | Strip all host credentials and halt on violation; refuse launch and quarantine on an exposed git config or an unsafe upstream |
| Docker control | Worker receives a Docker socket | No socket passed; capabilities dropped; worker's default identity is not the host's Docker-capable UID. The OpenShell gateway holds the Docker socket, behind mTLS on VM loopback; no worker or sidecar can reach it. `POST /runs`'s `sandbox_image` is gated by an explicit daemon-configured allowlist; `sandbox_docker`/`sandbox_user` are refused outright (session-config only). No `POST /runs` field, console setting, or CLI flag can select host execution on any path | enforced | Refuse launch and quarantine |
| Harness (Codex CLI) | The coding-agent CLI reaches a vendor service (ChatGPT backend, plugin marketplace, update check, analytics, feedback upload, hosted web search), uses its own sandbox, or reads a host auth file | Runs only inside the Docker sandbox: `codex` is baked into the digest-pinned worker image at an exact version (`@openai/codex@0.154.0`, installed `--ignore-scripts` from its own Node stage, root-owned). `CodexAdapter` (`agent/pi/scripts/harness_adapters.py`) points it at the route's real upstream only (`model_providers.relay` with `base_url` = `FACTORY_MODEL_BASE_URL`, Responses API; the descriptor's `WireAPIs` is `openai-responses` alone, so `sessionconfig.CheckHarnessAPI` refuses it on any other route), naming its key and headers by environment variable (`env_key`, `env_http_headers`, from `FACTORY_MODEL_KEY_ENV`/`FACTORY_MODEL_HEADERS_JSON`): those variables hold placeholders, never a real key, and the supervisor substitutes the credential. The route's policy admits the Codex executable and, on a `chatgpt-codex` route, the Responses path alone, so every other request to that host is denied (seen live: 403 `policy_denied` on the plugin export path). Its own sandbox is off (`--dangerously-bypass-approvals-and-sandbox`) because the worker container is the containment (no network interface; the supervisor is the only route out). Plugin sync, connector apps, analytics, feedback upload, update check and hosted web search are also off via `-c` (`features.plugins`, `features.apps`, `analytics.enabled`, `feedback.enabled`, `check_for_update_on_startup`, `web_search`); its five bundled system skills are off via `skills.bundled.enabled`. `CODEX_HOME` is `<session_dir>/codex-home` under the workspace session dir, never the host's `~/.codex`; agent stdin is `/dev/null` | enforced | Refuse launch (`prepare` exits without a model route or off the Responses API) and quarantine |
| Harness (Copilot CLI) | The coding-agent CLI authenticates to GitHub, reports telemetry, self-updates, loads web tools or the GitHub MCP server, trusts the repository's own hooks/plugins/MCP servers, or reads a host auth file | Runs only inside the Docker sandbox: `copilot` is baked into the digest-pinned worker image at an exact version (`@github/copilot@1.0.88`, `--ignore-scripts`, root-owned, its bundled package pre-extracted read-only and selected with `COPILOT_CLI_DIST_DIR`). `CopilotAdapter` runs bring-your-own-key against the route's upstream only: `COPILOT_PROVIDER_BASE_URL` = `FACTORY_MODEL_BASE_URL`, `COPILOT_PROVIDER_API_KEY` = the route's placeholder (the value of the variable `FACTORY_MODEL_KEY_ENV` names, which the supervisor substitutes; `factoryd-relay-placeholder` on a route with no credential) -- never a real key. On a route with a further credential header (`chatgpt-codex`) it sends that header's placeholder too (`COPILOT_PROVIDER_HEADERS`) and runs the CLI under `node fill_responses_output.mjs`, a loopback proxy inside the worker that the CLI uses as its base URL: it forwards each request unchanged to `FACTORY_MODEL_BASE_URL` and fills the final Responses event's empty `output` from the items the stream delivered (that backend sends items only as stream events and no content type; the CLI reads a turn from the final `output`). The proxy holds no credential, runs under the worker's `node` (already a model executable of the policy), and every request still leaves through the supervisor and the meter. Live-proven on a `github-copilot` route through the gateway (2026-10-04) and on a `chatgpt-codex` route (2026-10-05, json-merge-patch live-smoke fixture accepted with the execution role on `copilot`), `COPILOT_OFFLINE=true` (no GitHub authentication, telemetry, web tools, GitHub MCP server or auto-update), `COPILOT_AUTO_UPDATE=false` and `--no-auto-update`. Tool approval is `--allow-all-tools` only; `COPILOT_ALLOW_ALL=true` (which also trusts the repo's own hooks, plugins and MCP servers) is never set. `COPILOT_HOME` is `<session_dir>/copilot-home` under the workspace session dir; agent stdin is `/dev/null` | enforced | Refuse launch (`prepare` exits without a model route; `invocation` exits when a credential placeholder the route names is unset) and quarantine |

In the worker, pi/pifork get `--skill` (for the mount and for the repo's own `.agents/skills`, which codex also reads natively), codex/copilot a fresh copy in their per-session home every round. **Open residual:** a worker can create a same-name repo skill mid-run, which Copilot would prefer in a later round; `repo_skills` is scanned after each attempt so it shows in evidence | enforced | Refuse launch before any container starts |
| Cancellation | Worker leaves descendants alive after timeout | Every launch ends, on deadline, cancel or normal exit, with factoryd deleting the sandbox through the gateway (`sandbox.RunThroughRuntime`, bounded at two minutes), which removes the worker and supervisor containers; a delete that fails is reported with the attempt, and the run's own container removal (`RemoveRunContainers`, `ReconcileOrphans`) then removes them with `docker rm -f` by the `openshell.ai/sandbox-name` label. | Forge / PR review | A denied or later-invalidated run still gets pushed/opened/marked-ready, or an untrusted PR commenter steers a corrective build | `openEvidencePullRequest`, the `gh pr ready` flip, and the PR-open-only retry path (`internal/requestdriver/pr_review_driver.go`, `retry_pr_opener.go`) each require a fresh `release.Decision.Allowed` immediately before the side effect, not just a decision recorded once at accept time. `internal/forge`'s reviewer-comment mechanism is an allow-list (`AuthorPolicy.Trusted`, empty by default — fail closed) with a separate `BlocksReadyThreads` list so an untrusted human's open comment still blocks the ready-flip even though it can't trigger a build. | Compose services | A target repo's published `ports:` open a host port, let the worker reach something other than the run's own sidecars, or collide on one loopback port | Nothing is published on the host: `ParseFile` keeps each fixed TCP host:container mapping (`PublishedPorts`), `ValidateComposeServices` rejects two services publishing one port, and `ApplyToWorkerLaunch` sets `BG_COMPOSE_FORWARDS` and runs the worker command under the image's `bg-forward`, which binds only the worker's own `127.0.0.1`/`::1` and dials only `<service address>:<port>` on the run's internal `bg-compose-<run>` network, through the supervisor -- each service is one `allowed_ips` endpoint of the run's policy, and no other address or port is admitted. A bind failure stops the worker before its command runs. Unit-tested and real-engine-validated (`make live-compose`: Postgres, Kafka and Redis by address from a gateway-launched worker) | enforced in bounded slices | Reject the Compose configuration on a port collision; fail the attempt when a forward cannot bind |
| Sandbox runtime | A gateway, sandbox or supervisor image changes under the factory; the gateway runs without TLS or client authentication; an OpenShell upgrade changes what a restart or a credential push does | The gateway, sandbox and supervisor images are named by digest everywhere buildgate names them (`docker-compose.openshell.yml`, `openshell-gateway.toml.tmpl`, `make openshell-images`); the meter image is built from source and recorded by digest (`meter_image`). The gateway requires a client certificate (mTLS) and signs each sandbox's JWT; `LaunchSpec`'s filesystem policy makes Landlock a hard requirement. `factoryd doctor` checks that the pinned images are present, that the gateway and the meter answer, and that the gateway config has TLS and mTLS on. An OpenShell upgrade re-runs the gateway-restart and credential-push live tests (`OPENSHELL_LIVE=1 OPENSHELL_LIVE_RESTART=1 go test ./internal/openshell -run Live`). **Open residuals:** the meter's listener is plaintext on VM loopback with no caller check; OpenShell's own resource admission is off (bind mounts require it), so `LaunchSpec.Validate` is the only check on a launch's mounts | partial | Refuse the launch when the gateway is not reachable (`factoryd doctor -fix` starts it); the operator stops the gateway on a suspected compromise |

This matrix is evidence of the current boundary, not permission to operate
with the partial controls. Sandboxing is unconditional: `-sandbox-image`
(and `POST /runs`'s equivalent) has no built-in default -- every image is
built from source on the operator's own machine (`make install`, recorded
via `factoryd configure-images`), never published or pulled from a
registry, and an empty/unconfigured value is refused before any container
launches; there is no host-execution opt-out anywhere in factoryd. The
worker image bakes only this repo's own dependencies and a sandboxed
build has no package-registry network by default — a target project
needing another dependency needs its own image
(`make project-sandbox-image PROJECT_DIR=<path> BASE_IMAGE=<worker ref>`).
