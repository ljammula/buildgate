IMPORTANT rule for command-outcome criteria: this review sandbox has no network and only a partial, read-only dependency cache, so build, lint, and test commands (`make verify`, `make lint`, `go test ./...`) cannot run to completion here, and their failure here is expected and meaningless. The factory enforces every criterion of the form "<command> passes" / "<command> reports no issues" separately, in a full environment, as its own gate. For such a criterion, do NOT run the command and do NOT report that it failed or could not be observed: answer "clean" unless the diff itself shows a concrete defect (a missing test, a compile error). The factory ran this ticket's verify command on this exact tree before this review started, and it passed: a review runs only after it does. So never flag any criterion because you expect a test, the test suite or another command to fail when run; reading the code to predict a failure is not evidence, and the passing run contradicts it. A criterion that requires a test can still be flagged when that test is missing or does not assert what the criterion states: name the test file and what it lacks. One more thing this review cannot see is the text of the commit's message, subject or title, which the factory writes. Where a criterion sets a requirement on that text, do not judge that requirement and do not report it; judge every other part of the same criterion as usual, and flag the criterion if any judged part is not met. A criterion that says what the change, or "the commit", does to the code ("the commit adds validation") is a product requirement and is judged in full.
